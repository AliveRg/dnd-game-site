# Расширенный промпт и план для модели владельца

Ты сопровождаешь общий GitHub-репозиторий AliveRg/dnd-game-site. Владелец — AliveRg, дизайнер — rogovekartem-cpu. Прочитай docs/COLLABORATION.md. Цель — выпустить выбранное изменение дизайна на dungeons-bgd.ru с сохранением действующих заявок, админки, карт миров, Метрики, PostgreSQL и S3. Начни с проверки фактического состояния веток и приложения. Описанный ниже переход выполняется однократно. Для дальнейших задач начинай с раздела «Выборочный выпуск».

## Однократный переход и проверка состояния

1. Сверь адреса origin и upstream, SHA у origin/main, origin/codex/timeweb-deploy и upstream/main и их общего предка. При переходе версия сайта была 3305b06, исходный дизайн — a459437. Для будущих задач бери текущие SHA.
2. Проверь, что design/rogovik содержит исходный дизайн и совместимые технические изменения. Открой генератор, календарь, галерею, форму и карту. Тестируй запись и медиа в отдельном окружении.
3. Проверь, что main содержит версию боевого сайта. При первом переносе используй fast-forward, если история позволяет. Если ветки разошлись, изучи изменения и представь разницу владельцу. После настройки защиты используй PR.
4. В существующем приложении Timeweb Mysterious Cygnus (289123) проверь источник AliveRg/dnd-game-site и ветку main. Сохрани параметры окружения, домен и сертификат. Убедись, что push в дизайн не связан с публикацией основного сайта.
5. Проверь приглашение rogovekartem-cpu и правило main с обязательным одобрением PR. Различай отправленное и принятое приглашение. Повторная отправка требуется только при отсутствии доступа и действующего приглашения.

## Выборочный выпуск

1. Возьми конкретное поручение владельца: [что выпускать], [SHA дизайнера, если известен], [страницы и критерии]. Если владелец просит только план, опиши изменения и остановись до любого push или деплоя.
2. Обнови ссылки Git и создай короткую ветку release/название от актуальной origin/main. Просмотри git show и найди зависимости выбранной доработки. Перенеси только согласованные коммиты через cherry-pick -x, от старого к новому. При смешанном коммите адаптируй только нужный компонент. Для карточек проверь соответствие полей опубликованных миров и ссылок.
3. Проверь diff относительно origin/main. Сохрани форму заявки с тарифами, политику и согласие, админку /dragons, текущие контракты API, подключение к PostgreSQL с TLS, S3, Метрику и метатег Вебмастера. Возвращай календарь или генератор в production только по отдельному заданию владельца.
4. Используй Node 24 и lock-файл. Собери приложение, запусти относящиеся к задаче тесты. Проверь мобильный и настольный варианты. На тестовой базе пройди сценарий заявки и админки, если изменение их затрагивает. Не коммить .env, пароли, сессионные cookie и данные заявителей.
5. Запушь короткую ветку в origin и открой PR с base main. В описании укажи исходный SHA, видимый результат, список проверок и снимки для интерфейса. Передай PR владельцу на одобрение.
6. После одобрения и слияния проверь SHA деплоя в Timeweb, HTTP 200 у /api/health, БД ok у /api/ready и целевую страницу на основном домене. Для заявки подтверждение — запись, доступная в админке. Для карты — список миров и открытие выбранного сюжета. При сбое зафиксируй конкретную ошибку и известный рабочий деплой.
7. В конце сообщи ветки, SHA, ссылку на PR, результат проверок и оставшиеся ручные действия. Не считай публикацией сам push в рабочую ветку.
